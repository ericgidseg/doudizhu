# MCTS 增强方案

现有实现：`ai_douzero.py` 里的 `_mcts_pick`（ISMCTS + belief-state 采样对手手牌）。
**不是从零做，而是修 + 增强。**

> **结论速览（2026-10-16）**
> - MCTS **默认关闭**（`USE_MCTS=0`）。修完所有已知 bug、权重调到最优之后，
>   它**依然显著更差**：200 局配对 关 0.405 / 开 0.350，差 **−0.055（z=−2.22）**。
> - 一路上的收获是**修 bug**：`other_hand_cards` 特征错误一项就带来
>   **胜率 0.200 → 0.400（z=+11.87）**，远超 MCTS 本身的任何收益。
> - 核心教训：MCTS 变差的原因不是"采样不够"（提速 21 倍后依然差），
>   而是 blend 的**尺度不匹配**（Bug 3）。且"两个信号不相关"推不出"谁更差"（0.6 节）。
>   修掉尺度问题只把危害从 −0.15 减到 −0.055，**没有转正** ——
>   说明 rollout 这个信号本身的增量信息就不够，不是调参能救的。

## 已修的 bug

### Bug 0（最严重）: `other_hand_cards` 特征算错 —— 每次决策的输入都是错的

`decide()` 里：

```python
# 原实现
my_played = played_cards_dz.get(seat, [])
for c in my_dz + my_played:      # ← 只减了「自己」出的牌
    all_cards.remove(c)
other_hand = all_cards
```

DouZero 的 `other_hand_cards` 定义是**另外两家的当前手牌**（见 `env/game.py`：
`other_hand_cards = 另两家 player_hand_cards 之和`），也就是

```
全副牌 - 我的手牌 - 三家所有已出的牌
```

只减自己的，等于**对手打过的牌仍被算作还在他们手里**。

**实测**：跟 `env/` 真值逐字段比对，66 次决策里 **62 次**该字段错误，
多出 5~12 张牌。也就是说喂给神经网络的特征一直是错的。

**修法**：改成减掉三家的已出牌（`played_by_pos.values()` 全部）。
修完 33 次决策 **0 次**错误。
参考实现见 `test_replay.py:55`（那里用的是 `my_hand + played`，`played` 是所有家的）。

**效果（600 局配对 A/B，同一副牌，`bench_otherhand.py`）**：

| | 地主胜率 |
|---|---|
| 修复前 | 0.2000 |
| 修复后 | **0.4000** |

配对差值 **+0.2000**，标准误 0.0168，**z = +11.87**（远超 1.96 的显著门槛）。
两版结果相同的局占 79%，说明差异集中在 21% 的关键局上 —— 正是那些
「对手已经打光了某花色、但 AI 还以为在他们手里」的局面。

### Bug 1: rollout 里两家 pass 后领出权给错人

`_rollout` 原代码：

```python
if consecutive_pass >= 2:
    cur_last = []
    cur_last_pos = turn_pos   # ← 覆盖成「最后 pass 的人」
    consecutive_pass = 0
    turn_pos = cur_last_pos   # ← 于是领出权给了 pass 的人
    continue
```

斗地主规则是**最后出牌的人**领出，不是最后 pass 的人。这行把 `cur_last_pos`
覆盖掉了，导致每次"两家 pass"后 rollout 都走错分支。

**影响**：所有 rollout 的后续走法全错，MCTS 的胜率估计被系统性污染。
**验证**：`landlord` 出牌 → 两家依次 pass → 第 4 次决策应该回到 `landlord`，
修复前是 `landlord_up`。

### Bug 2: `q_spread > 0.7` 判据在 vote 模式下恒成立

`decide()` 里原本用 Q 值绝对跨度判断"这步很容易，跳过 MCTS"：

```python
q_spread = float(values.max() - values.min())
is_easy = ... or (q_spread > 0.7)
```

但 `_vote_values()` 会把三个模型的 Q 值 **min-max 归一化到 [0,1]** 再平均，
所以跨度恒在 [0.33, 1.0]，均值 0.84 —— **80.6% 的局面都被判为"容易"而跳过 MCTS**。

**实测**：修复前 MCTS 只触发 15%（9/58 次决策），修复后 42%（25/59）。
**修法**：改用「最优与次优的差距 ÷ 整体跨度」，接近 1 才是真的碾压。

### Bug 3: `_mcts_pick` 的 blend 尺度不匹配 —— MCTS 经常帮倒忙

```python
refined[i] = 0.3 * base_values[i] + 0.7 * (wr * 2 - 1)
```

这里**有两个**问题，第一个修完才发现第二个，第二个才是真正致命的。

#### 3a. 量纲不一致（第一次修）

`base_values` 在 vote 模式下是 min-max 归一化到 **[0,1]** 的，
但 rollout 项 `(wr*2-1)` 在 **[-1,1]**。两者相加再跟
**没参与评估、仍保持 [0,1] 原值**的动作比大小 —— 尺子不一样。

后果：top-K 里最好的动作，rollout 胜率要 **>0.85** 才能不被
「压根没评估过的普通动作」反超。胜率 0.5 时 refined≈0.30，
直接被未评估的 0.68 碾压。

**修法**：rollout 项改用 `wr`（[0,1]）。

#### 3b. 分布不匹配（第二次修，真正的原因）

改完 3a 之后 MCTS **还是**更差。因为两者虽然都在 [0,1]，
但**分布完全不同**：

| 信号 | 取值范围 | 典型区间 |
|---|---|---|
| `base_values`（vote 归一化后） | [0,1] | **0.85 ~ 1.00** |
| rollout 胜率 `wr` | [0,1] | **0.20 ~ 0.60** |

斗地主地主整体胜率就只有 30~40%，所以 `wr` 天然集中在 0.2~0.6。
于是 `0.3*Q + 0.7*wr` 平均只有 `0.3*0.9 + 0.7*0.35 = 0.52`，
**反而低于**那些「未参与评估、保持原值」的普通动作（0.84）。

实测：6 个 top-K 动作里有 **4 个**被未评估动作反超。
也就是说 MCTS 评估得越认真，那个动作越容易被踢出局 —— 完全反了。

**关键认识**：rollout 胜率的**绝对值没有意义**，只有**相对排序**
携带信息。所以必须把它映射到「被比较的那批 Q 值」的区间上，
而不是直接混进 [0,1]：

```python
vals = [win_count[i] / tries[i] for i in top_idx if tries[i] > 0]
cand_q = [base_values[i] for i in top_idx]
q_lo, q_hi = min(cand_q), max(cand_q)
wr_lo, wr_hi = (min(vals), max(vals)) if vals else (0.0, 1.0)
wr_span = wr_hi - wr_lo

for i in top_idx:
    if tries[i] > 0:
        wr = win_count[i] / tries[i]
        if wr_span > 1e-9:
            wr_scaled = q_lo + (wr - wr_lo) / wr_span * (q_hi - q_lo)
        else:
            wr_scaled = (q_lo + q_hi) / 2.0
        refined[i] = (1 - w) * base_values[i] + w * wr_scaled
    else:
        refined[i] = base_values[i] * 0.5      # 未评估的压到下半区
```

修完实测：**0/6** 被反超（原来 4/6）。

**教训**：这类 bug 不会报错，只会让增强手段悄悄失效 —— 测出来就是
「MCTS 没效果」，很容易误判成「MCTS 没用」。而且「量纲一致」不等于
「可比」：两个信号都在 [0,1]，只要**分布**不同就依然不可比。

## 增强方向（按性价比排序）

### 0. ⚠️ 曾经的假设：rollout 数量不够 —— 后来被证伪

> **这一节的结论是错的**，保留它是为了记录推理过程。真实原因是 Bug 3
> 的 blend 尺度不匹配（见 0.5 / 0.7 节）：提速 21 倍把采样噪声从 ±0.29
> 降到 ±0.019 之后，MCTS **依然**更差，说明瓶颈从来不是采样数量。

`_mcts_pick` 对 top-K=6 个动作各跑 rollout，用**平均胜率**去修正 Q 值。
问题是一次 rollout 要跑完整局（几十步、每步一次 ONNX 推理），所以
**时间预算内能跑的 rollout 数极少**：

| 预算 | 每步 rollout 数 | 每个动作采样数 | 胜率估计标准误 |
|---|---|---|---|
| 0.3s | 16 | **2.7** | ±0.29 |
| 1.0s | 54 | 9 | ±0.17 |
| 3.0s | 162 | 27 | ±0.09 |

而斗地主里两个合理动作的真实胜率差通常只有 **0.05~0.15**。
也就是说 **噪声是信号的好几倍** —— 用这种估计去"改进" Q 值，
等于把原本准确的判断覆盖成随机值。

**实测**（`bench_paired.py`，同一副牌配对，budget=0.3s）：

| 局数 | MCTS 关 | MCTS 开 | 差 |
|---|---|---|---|
| 50 | 0.440 | 0.380 | −0.060 |
| 100 | 0.430 | 0.340 | −0.090 |
| 150 | 0.400 | 0.307 | −0.093 |

MCTS 开了之后**更差**。同时测得 MCTS 会改变 **31.7%** 的决策
（303 次里改了 96 次）—— 它确实在起作用，只是作用方向是负的。

**直接证据**：同一局面，用 n=5 次采样估计胜率，与 n=200 次的近似真值对比：

| 动作 | n=5 估计 | 真值(n=200) | 误差 |
|---|---|---|---|
| `[3]` | 0.400 | 0.230 | +0.170 |
| `[4]` | 0.600 | 0.315 | +0.285 |
| `[5]` | 0.200 | 0.325 | −0.125 |
| `[6]` | 0.000 | 0.160 | −0.160 |

n=5 时的排序是 `[4] > [3]`，而真值排序是 `[5] > [4] > [3]` ——
**MCTS 会因此选错动作**。误差量级（±0.13~0.29）远超动作间的真实差距。

**要让噪声低于真实差异，每个动作需要 44~400 次采样**，
按当前 rollout 速度就是每步几十秒到几分钟 —— 实际对局不可接受。

**这个分析本身没错，但结论错了**：按它去提速（见 0.5），采样数从 2.7
提到 714，噪声远低于真实差异了，MCTS 却**更差**。所以噪声不是主因，
真正的病根在 blend 的尺度（Bug 3）。

### 0.5 ✅ 已做：启发式 rollout 提速 21 倍 —— 但 MCTS 依然有害

按上面的分析，第一步是让 rollout 变快。已实现（`USE_FAST_ROLLOUT`，默认开）：

用启发式策略（出最小代价的牌、队友领先时让路、炸弹留着）替换 rollout 里的
神经网络，省掉每步一次 ONNX 推理：

| rollout 策略 | 耗时 | 2.5s 预算下每动作采样数 | 估计标准误 |
|---|---|---|---|
| 神经网络 | 9.60 ms | 22 | ±0.11 |
| **启发式** | **0.45 ms** | **714** | **±0.019** |

**提速 21.5 倍**，采样噪声从 ±0.11 降到 ±0.019，已经远低于动作间真实差距
（0.05~0.15）。按理说这时候 MCTS 该有用了。

**但配对 A/B 显示它仍然更差**：

| rollout 策略 | MCTS 关 | MCTS 开 | 差 |
|---|---|---|---|
| 神经网络（150 局） | 0.400 | 0.307 | −0.093 |
| 启发式（60 局） | 0.450 | 0.300 | **−0.150**（z=+2.42，A 显著更好）|

**差距没有缩小，反而更大**。所以瓶颈不是采样数量。
（这是当时 blend 尺度还没修的结果；修完之后危害减到 −0.055，
但依然显著为负，见 0.7 节。）

### 0.6 关于「rollout 与 Q 值不相关」—— 一个我犯过的推理错误

测了 12 个局面，对每个局面取 Q 值 top-5 动作，各跑 200 次 rollout，
算「rollout 胜率排序」与「Q 值排序」的 Spearman 相关性：

```
平均 = +0.040    各局面 = [+0.10, +0.90, -1.00, +0.10, +0.10]
```

**基本不相关**。一个直观例子（地主第一步）：

| Q 排名 | 动作 | Q 值 | rollout 胜率 |
|---|---|---|---|
| 1 | `[3]` | 0.977 | 0.147 |
| 3 | `[4,4]` | 0.958 | 0.240 |
| 5 | `[5,5]` | 0.899 | **0.293** |

⚠️ **但「不相关」不等于「rollout 更差」**。我一开始就是这么推的，
这是错的 —— 相关性只说明两个信号**不一致**，不说明**谁对**。

后来换了个测法：用 vote 集成（当前最强策略）打完整局当「真值」，
看哪个信号的排序更接近真值：

```
与真值的 Spearman:  启发式 rollout +0.536   神经网络 rollout +0.557   Q 值 +0.300
```

**rollout 反而更接近真值。** 当然这个测量本身有问题（`_build_belief`
采样的对手太弱，有些局面真值全是 1.00，区分不出来），样本也小（8~14 个局面），
不能当定论。但它足以说明：**「+0.04」不能拿来给 rollout 判死刑。**

真正让 MCTS 变差的是 Bug 3b 的**分布不匹配**，不是 rollout 本身不准。
修掉之后 MCTS 的表现见下一节。

### 0.7 修完 Bug 3b 后的权重扫描 —— 以及一次被噪声骗到的经历

修完分布映射之后，混合权重 `w`（`refined = (1-w)*Q + w*wr_scaled`）
需要重新标定。各跑 100 局配对（基线 MCTS 关 = 0.3900）：

| `MCTS_BLEND_W` | MCTS 开 | 净效果 |
|---|---|---|
| 0.7（原值） | 0.2833 | −0.100 |
| 0.5 | 0.3083 | −0.075 |
| **0.3** | **0.4000** | **+0.010** |
| 0.2 | 0.3500 | −0.040 |

100 局的标准误是 ±0.049，所以 0.3 的 +0.010 **完全在噪声内**。
当时我的判断是「修掉分布 bug 把 MCTS 从 −0.09 拉回到 ≈0 的中性」，
并把 0.3 定成了默认值。

**200 局复测推翻了这个判断**：

| 局数 | MCTS 关 | MCTS 开 (w=0.3) | 差 | z |
|---|---|---|---|---|
| 100 | 0.3900 | 0.4000 | +0.010 | — |
| **200** | **0.4050** | **0.3500** | **−0.0550** | **−2.22** |

`z = −2.22`，**MCTS 开显著更差**。0.3 那格 +0.010 纯属噪声，
样本一翻倍就变回 −0.055 —— 和 0.5、0.7 的差距只是程度不同。

**最终结论**：修掉分布 bug 确实让 MCTS **变好了一点**（−0.100 → −0.055），
说明诊断是对的；但它**没有转正**，仍然显著有害。

**教训**：100 局配对的标准误 ±0.049 意味着**任何小于 0.05 的效应都测不出来**。
看到 +0.010 这种"微弱正向"时，正确反应不是"有希望，继续调"，
而是"这个样本量根本分辨不了，必须加大样本"。我用一个噪声级的读数
定了个默认值，然后又花 200 局才发现它是错的。

### 1. ✅ 已完成：轻量 rollout（见上面 0.5 节）

启发式策略已实现并通过 `USE_FAST_ROLLOUT` 开关（默认开）：
- 能一把走完就走完
- 农民队友领先时让路（对手快走完时除外）
- 否则出**代价最小**的合法动作（牌面代价 + 拆对子/三张加权）
- 只有炸弹能压时，对手不急着走完就先留着

**结果**：快 21.5 倍，但 MCTS 依然更差 —— 瓶颈不是采样数量，
而是 blend 的尺度问题（Bug 3）。见 0.6 / 0.7 节。

### 2. ✅ 已做：belief 采样改成 Gumbel top-k —— 权重曾被严重稀释

`_build_belief` 有一套规则（pass 历史降权、炸弹降权、叫分加权），
但旧采样器 `_sample_hands_old` **几乎没把权重当回事**。

**诊断方法**：构造一张"特殊牌"，其 belief 比值 r，其余牌都是 1.0，
看它落到 opp0 的概率。理想曲线应随 r 单调、r=1 时等于 n0/N。

```
比值 r          r=1     r=5     r=20    r=100
理想            0.500   ~0.95   ~0.99   1.000
旧实现          0.506   0.797   0.898   0.931   ← 曲线被压平
Gumbel          0.518   0.948   0.999   1.000
```

**r=100（信号强度 100:1）时旧实现只给 0.93** —— 信号最强的地方最不听话。
而 `_build_belief` 的规则会产生 0.4/0.6/0.85 这类系数，叠乘后能到 0.1 以下，
正好落在被压平的区间。

第二个独立验证（"大牌不太可能在 A 手里"，权重 0.2）：

| | A 拿到大牌(≥10)的平均张数 |
|---|---|
| 理论 | 0.455 |
| 旧实现 | **0.866**（偏差 +90%）|
| Gumbel | 0.523（偏差 +15%）|

**旧采样器让 A 拿到近两倍的大牌**，belief 信号基本被无视。

**病因**（旧代码）：
```python
w0 = beliefs[opp0].get(c, 1.0) * max(remaining[opp0], 0.1)   # ← 病根
```
把"张数约束"和"belief 权重"乘进同一个数里，两者互相干扰。

**修法**：Gumbel top-k —— 按 log-odds 加 Gumbel 噪声排序，取前 n0 张。
随机性和硬约束**解耦**，排序天然保证张数精确。

```python
key = np.log(b0) - np.log(b1) + np.random.gumbel(size=len(pool))
order = np.argsort(key)[::-1]
```

**验证**：r=1 时无偏（6 种张数比例偏差都在噪声内）；2000 次随机测试
**零违反**张数约束。开关 `AI_OLD_SAMPLER=1` 可切回旧实现做 A/B。

**但注意适用范围**：`_sample` 只在 `_mcts_pick` 里被调用，所以这个改进
**只在 MCTS 开启时生效**。MCTS 默认关，且已知 z=−2.22 显著更差 ——
所以它最多只能把 MCTS 拉回 0 附近，不会直接让 AI 变强。

**决策分歧率实测 3.0%**（203 个地主决策点里 6 次改变动作）。
即一个*完美*的采样器也只能通过这 3% 的决策起作用 —— 收益天花板很低。

其余可增强点（未做）：
- **手牌数约束**：对手只剩 2 张时，他手里有炸弹的概率应大幅降低（已部分实现）
- **记牌器**：已出的牌从池里移除（已实现），但**没利用"某人一直没出某花色"这类信号**

### 3. 树结构（现在是 flat，不是真 MCTS）

当前 `_mcts_pick` 是对 top-K 动作各跑若干 rollout 取平均胜率 —— 本质是
**flat Monte Carlo**，没有树的扩展/选择/回传。

真正的 ISMCTS 会有：
- 树的 UCB 选择 → 好分支分到更多预算
- 信息集级别的复用（同一信息集跨多次采样共享统计）

**收益**：同样时间预算下，预算集中在有希望的分支上。
**代价**：实现复杂度高，需要重构 `_mcts_pick`。

### 4. 时间预算利用

现在 `budget = min(5.0, max(0.3, time_left - 0.5))`，服务器给 30s，只用 5s。

- 可以按局面复杂度动态分配（`n_legal` 大 → 多给时间）
- 简单局面早停（已有 `min_rollouts` 机制）
- **注意**：用满 30s 会让玩家等很久，需要权衡。建议 5-8s。

| 步骤 | 内容 | 结果 |
|---|---|---|
| ✅ 已完成 | **修 `other_hand_cards` 特征错误** | **胜率 0.200→0.400（z=+11.87）** |

| ✅ 已完成 | 加队友感知 rollout | 已实现 |
| ✅ 已完成 | **启发式 rollout 提速 21 倍** | 0.45ms/次，每动作采样 714 次 |
| ✅ 已完成 | blend 权重扫描 | 0.7→0.3，危害从 −0.100 减到 −0.055 |
| ❌ 结论 | **MCTS 依然显著更差**（200 局 z=−2.22） | **默认关闭，不再调** |
| — | 若要继续：真 ISMCTS 树 + 网络先验（AlphaZero 式） | 未开始 |

**四条重要教训**：

1. **Bug 0 修好之前，所有关于「MCTS 有没有用」的测量都是无效的** ——
   基线本身（`decide()` 的策略网络输入）就是错的。
2. **采样数量不是瓶颈**。提速 21 倍、噪声降到 ±0.019 之后 MCTS 依然更差，
   真正原因是 blend 的尺度不匹配（Bug 3b）。只盯着"多采样"会一直在
   错误的方向上优化。
3. **「两个信号不相关」推不出「谁更差」**。我一开始从 Spearman +0.04
   直接推出"rollout 更差"，这是逻辑跳跃 —— 相关性只说明不一致。
   后来用 vote 集成当真值测，rollout 的排序反而更接近真值（+0.54 vs +0.30）。
   判断一个信号好不好，要拿**真值**比，不能拿**另一个信号**比。
4. **修好 bug 不等于问题解决**。Bug 3 的诊断是对的（危害 −0.15 → −0.055），
   但修完 MCTS 仍然显著为负。**诊断正确 + 修复到位 ≠ 方案可行** ——
   该放弃的时候要放弃，别因为"已经修了这么多"就继续投入。

## 怎么验证有效

**不要用自对弈 LL_WR**（见 `models_v2/README_警告_勿用.md`，那个指标会误导）。

**首选 `bench_paired.py`** —— 同一副牌跑两个配置，方差比独立采样小得多：

```bash
AI_USE_MCTS=1 AI_MCTS_BLEND=0.3 ORT_NUM_THREADS=2 \
  python3 -u bench_paired.py -n 200 \
  --a decide --b decide --a-mcts 0 --b-mcts 1 --time-left 25
```

`bench_mcts.py` / `arena_vote.py` 也能用，但独立采样要更多局才等效。

判定标准：**配对差值显著 > 0**（看脚本输出的 z 值，|z| > 2 才算显著）。
注意 100 局的标准误是 ±0.049，所以 100 局的结论基本只能看方向。

⚠️ 读结论时确认符号：`diffs` 是 **A−B**。
